# ADR 0006: evidenced archive fields and a versioned cleanup successor

Status: non-destructive engineering framework and protocol proposal for review; **P6-ARCHIVE remains open**. Base: integration `ebeedf4`. Date: 2026-09-27.

## Implemented boundary

`ArchiveLifecycle.swift` inventories every encoded field in `LegacyLibraryArchive` tracks, queue, model archives and settings. Model fields are read from their actual JSON, so new fields are not silently discarded. Nested queue JSON, base64 snapshot data and plist settings are opaque fields; classifying an entire opaque value as user input requires evidence for its entire content. No recursive removal is attempted. Raw original SQLite stores and separate physical capture manifests are outside this API's inventory; they must be included in the destruction manifest described below. In particular, the reader's physical `CatalogArtist`/`CatalogRelease` manifest is not the same thing as `LegacyLibraryArchive.models`.

Default classification is `unknown`. `ArchiveEvidence` binds a review reference, source category, original fetch time and (for authorized data) an opaque authorization-lineage reference to one field address and its exact canonical JSON SHA-256. Edited bytes invalidate the evidence. Duplicate, stale, absent-field or incomplete authorized evidence fails. Nothing labels a title as user-authored because it looks edited, assigns a migration date as a fetch date, or infers authorization from a provider/video ID. Review references are trusted engineering input, not proof obtained by parsing arbitrary imported JSON; production must not accept self-asserted evidence from users or backups as verified provenance.

| Category | Evidence required | Assessment / successor |
| --- | --- | --- |
| User input | Field-specific reviewed write contract or recorded user-edit lineage, matching current bytes | Preserve exact JSON value in `userFields`, unless explicitly excluded by deletion |
| Public API | Reviewed response/capture lineage, matching bytes, original fetch time | API category remains distinct; evaluate inherited deadline; never copy value into `userFields` |
| Authorized API | Same plus a non-secret authorization lineage reference | Same; reported revoked authorization makes removal due immediately |
| Unknown or mixed | Missing/insufficient evidence, including opaque snapshots with uncertain contents | Unresolved; preserve original untouched, block release review; never grant a new TTL |

The old `NotesService.setTrackNote` and `NotesSheets` TextEditor provide a candidate source contract for note content. Bookmark titles, playlist names and favorites need all writer/default/import paths reviewed before blanket classification. This commit deliberately ships no blanket legacy allowlist. The physical fixture test marks only its known synthetic note content as user input; other content stays unresolved. New public `.user` metadata provenance does not retrospectively establish origin for historical raw archives.

The injected clock and policy interval are evaluated without scheduling or mutation. Tests use 29 days as an engineering margin. Missing/future API fetch dates are removal-due, not renewed. Unknown source is unresolved, not implicitly API or implicitly user. Authorization references never contain tokens, cookies or raw account IDs. Revocation must be supplied from a separately validated integration; this module does not contact Google. A date evaluation does not establish that cleanup ran while the app was asleep.

`ArchiveSuccessor` version 1 contains the parent archive digest, the **unchanged original import receipt**, assessments, exact evidenced user fields and exclusions. The receipt still describes the complete original import; it is not a receipt for cleaned content. Assessments contain digests and review/authorization references, which may themselves remain linkable data and require retention review. This is not a claim that the entire successor is anonymous or exempt from policy.

`stageArchiveSuccessor` is an explicit engineering API, not called by startup, hourly maintenance or UI. It verifies the parent digest, historical receipt, complete field coverage and preservation projection, and saves a new migration-kind row. It does not rewrite original archive records, projections, source files, active routing or receipt. An existing stage cannot be overwritten with a less restrictive plan. The existing `restoreOriginalPlaylist` path rejects a staged marker, including malformed marker payloads, before touching tracks. Disk-reopen and physical legacy tests verify this barrier and unchanged parent digests. Existing public behavior is unchanged until a caller explicitly stages a successor.

This local barrier is intentionally conservative: it blocks whole-archive playlist restore. It is not yet a cross-backup deletion tombstone, nor a complete per-item erasure feature. Current archive viewing/export, normal public rows and original files remain present. An older binary or independently restored backup can bypass a marker stored only in the active database. The production protocol below must address this before any old copy is destroyed or a deletion claim is made.

`ArchiveRemovalJournal` version 1 is a serializable protocol state with a closed set of artifact IDs. Its injected removal and independent absence probe support synthetic-file tests. Failure, surviving bytes, or an unlisted ID cannot count as verified absence. Successful retries clear that artifact's failure state. There is **no production filesystem removal adapter or automatic executor** in this commit. `allListedArtifactsAbsent` means exactly that list, not that a user's entire data footprint or external backup has been erased. Caller persistence before/after operations is required and not implemented by the value type.

## Proposed production successor protocol (not activated)

1. Inventory the active route plus every owned copy before planning. Record stable artifact identity, location, generation, expected digest, main/WAL/SHM membership, reference graph, source provenance and whether it is the sole copy of any user field. Include partial attempts and failed snapshots. Refuse unaccounted files, changed bytes, unsupported versions and concurrent writers; do not silently reduce scope.
2. Produce an explicitly reviewed field manifest. Separate local IDs/relations required for notes, bookmarks, favorites and playlist occurrences from API identifiers and content. For opaque nested data, implement version-specific decoders with full coverage tests or leave it unresolved. A note associated with a deleted video needs an agreed orphan-note representation. Unknown custom metadata needs user review/export or a clarified lawful/policy disposition; do not delete the whole mixed record to simplify implementation.
3. Build a new SQLite generation from the preservation manifest and permitted current public data. Reapply every previously durable deletion exclusion. Do not edit the old database in place or overwrite its receipt. Record a new successor identity and independent successor content digest linked to the old receipt, with only the minimum approved lineage retained. Reopen independently and compare all preserved values/IDs/relations. This framework's `userFields` is a reviewable extraction, not yet that complete runnable library.
4. Before any destructive work, atomically publish and fsync a versioned external lifecycle marker in the route root, outside databases being replaced. It must bind the exact successor, manifest digest, excluded entity/field IDs, reviewed destruction authorization, required artifact set and state `cleanupPending`. Publish only after candidate verification. Startup must never fall back to an old source/old candidate when that marker exists, even if its successor is missing or corrupt. Whole-app deletion takes precedence. Backward-incompatible markers must fail closed in updated readers; older-binary/backup restoration limits must be explicitly handled and disclosed.
5. On a later process launch with no old database handles, perform only the authorized manifest removals. Recheck identity/digest, remove main/WAL/SHM as a set, synchronize affected directories and independently verify absence. Persist each result; a crash after unlink but before journal save retries idempotently. Any filesystem denial, missing permission, changed file or new unlisted copy leaves cleanup pending and the restore barrier in force. Logical row deletion is insufficient because SQLite free pages/WAL or snapshots may retain payloads; use the verified new generation and retire the whole old artifact set.
6. Only after all required artifacts are verified absent may the route declare that particular physical cleanup complete. Keep minimal approved non-resurrection state independently of the removed generations. Never infer global erasure from filenames, encryption, UI concealment, a different archive label or hashes alone. Re-inventory to detect stale copies. A candidate/store loss fails closed and needs recovery; it does not authorize reimport.
7. Test real process kills at candidate save, marker publication, each artifact removal, completion publication and restart; save/fsync failures; wrong source digest; old active marker; orphan sidecars; missing successor; external backup restoration; revoked lineage; inherited expired/future/missing times; and user edits made while cleanup is pending. Preserve current public edits when preparing the successor and exclude late API responses. Do not attach this protocol to automatic expiry until these acceptance tests and the external gates pass.

## Exact protected scope and external gates

| Gate / owner | Scope and reason | Required evidence / decision |
| --- | --- | --- |
| User / product authority for destructive migration | Original legacy main/WAL/SHM; old default public store; every UUID migration attempt, `snapshot-input-*`, SQLite snapshot and candidate; capture/model manifests containing original scalar values; archived raw queue JSON; imports/revisions/shadows/sync payloads; archived settings; sole recoverable custom titles/lyrics/notes/playlist edits | A verified successor containing every proven user field, explicit resolution of unknown user edits, and authorization covering retirement of these originals/unique backups. This task authorizes the framework, not destruction of those real artifacts. Existing explicit whole-app deletion remains a separate user action. |
| Google policy interpretation / release owner | API/authorized/unknown content in all retained copies, plus linkable digest/lineage records; apps unlaunched beyond retention windows; historical fallback/recovery behavior | Resolve against applicable policies and obtain a written Google determination if relying on an exception or disputed archival use. No Google approval is asserted, and ordinary policy-required deletion is not claimed to require a new Google permission. User consent alone cannot waive Google retention rules. |
| User-owned / external backups | Files exported outside the app's owned directory, OS/device backups, shared copies and previously shipped app containers | Determine controllable scope and backup-restore exclusion mechanism. No silent remote deletion or claim of physical erasure of inaccessible backups. Any required user action must identify actual copies and consequences. |
| Integration / release reviewer | Active API projections, notebook edits, item removal, restore/export UI, route authority, clock/revocation triggers and every copy above | Wire one tested authority across all routes and give accurate pending/completed scope. This commit's staging guard alone does not close resurrection or deletion obligations. |

The current [YouTube Developer Policies](https://developers.google.com/youtube/terms/developer-policies) III.E.4 distinguishes storage categories and requires refresh/deletion for applicable data; III.E.4.g and III.E.2 address deletion requests and revocation. These obligations cannot be met merely by withholding display or renaming/encrypting retained bytes. No archival exception or indefinite-storage authorization was established by this work.

## Validation

- Persistence package: 33 tests passed, including six new lifecycle tests (mixed fields, bound evidence, simulated time/revocation, unknown-field inventory, synthetic removal failure/retry/reopen, staged barrier/disk reopen).
- Root physical migration suite: `swift test`, 11 tests passed. The new physical fixture test stages the successor, preserves original receipt/archive/source fingerprints and blocks archive restore while the existing verified active route still opens.
- Isolated iOS physical migration suite: 11 tests passed on iPhone 17e / iOS 26.5 simulator. These tests compile and exercise the persistence module with the exact old-model reader. No claim of production physical cleanup or new Release signing validation is made.
- No real user database, account or credentials were inspected or deleted. No push, deployment, policy publication or Google request was performed.

Remaining release gates: reviewed field contracts and opaque decoders; complete artifact inventory; verified playable/user-editable successor; external durable cross-route exclusion; production cleanup implementation and process-kill tests; retained-copy/backup and suspended-app policy resolution; required user authorization for unique originals. **P6-ARCHIVE is not complete.**
