## Scope and evidence boundary

The public source/dependency allowlist is [project.yml](../../project.yml), target `Muses`. Inherited infrastructure elsewhere in the repository is not evidence of active public-build behavior. The active composition has no developer-operated backend endpoint, analytics SDK, or advertising SDK dependency observed in this snapshot. That finding does not establish zero collection: Google's embedded player, API, thumbnails and authentication are external services.

The [privacy gate](../../Sources/Muses/Features/Public/PublicPrivacyView.swift) and [composition root](../../Sources/Muses/App/PublicYouTubeApp.swift) defer `PublicYouTubeSession` construction until the versioned agreement is accepted. The agreement starts unchecked, missing policy content prevents acceptance, and the fixture bypass is DEBUG-only. Acceptance is stored under `muses.privacy.acceptedVersion` in UserDefaults. This supports **no automatic feature/session initialization before agreement** by source inspection, not a measured claim of no network traffic. Explicit provider/support links remain available before acceptance. A previously accepted version permits initialization, including token refresh, on the next launch. This agreement is not an ATT authorization.

Apple documents [ephemeral URLSession behavior](https://developer.apple.com/documentation/foundation/urlsession), the [persistent default WebKit store](https://developer.apple.com/documentation/webkit/wkwebsitedatastore), and [AsyncImage's shared URLSession](https://developer.apple.com/documentation/swiftui/asyncimage). These are different storage boundaries. Foundation's [file-system guidance](https://developer.apple.com/documentation/foundation/using-the-file-system-effectively) includes Application Support in normal backups; no backup-exclusion assignment was found in the active source reviewed. User truth can therefore participate in device backups subject to Apple settings. A local wipe must not promise deletion of historical Apple backups, data already received by Google, or system-browser sessions.

## Google embeds, App Privacy and ATT

YouTube's binding policy explicitly describes player data transfer both on loading and playback (III.E.9). Google describes identifiers, device/browser details, IP, search/video/ad activity and settings-dependent processing in its [privacy policy](https://policies.google.com/privacy). That broad provider policy is evidence against an unsupported zero-collection claim; it is not a build-specific list of every field actually collected in Muses.

Apple's [App Privacy definitions](https://developer.apple.com/app-store/app-privacy-details/) include integrated third parties and functional web views. Collection depends on off-device access beyond servicing a real-time request; optional sign-in alone does not exempt ongoing core-feature data. The following is a review worksheet, **not finalized ASC answers**:

| Candidate disclosure | Evidence from this app; remaining question |
| --- | --- |
| Search History | Native query strings leave the device. Establish Google's retention and uses for the actual API integration. |
| Product Interaction / Advertising Data | Video selection/playback and embedded ads; establish what the player retains and whether ad impressions/interactions are associated with users. |
| User ID / Device ID | Authorized requests identify a Google account; WebKit identifiers/cookies may persist. No native IDFA call observed. Determine actual identifiers and linkage rather than treating an API key as a user ID. |
| Coarse Location / Diagnostics / Other Data | IP and request/device context reach Google. Determine actual downstream use; do not automatically equate every IP with location collection or assume all possible Google diagnostics are present. |
| Other User Content / Customer Support | Native notes/bookmark labels stay local in reviewed code. Public Issues content is deliberately submitted through an external browser. Assess that distinct support route before assigning any disclosure exemption. |

For each actual collected type, the owner must substantiate purpose, retention, linkage, and tracking against the exact embedded product/configuration. Keep provider evidence and redacted runtime observations together. Native scope and code inspection cannot establish Google's server retention, advertising joins, regional/account variations, or linked-versus-unlinked treatment. A single traffic capture also cannot prove their absence.

Apple's [ATT guidance](https://developer.apple.com/app-store/user-privacy-and-data-use/) covers cross-company data linkage for advertising/measurement and applies to functional web views. Tracking does not require IDFA. Ads do not by themselves prove tracking, and cookies/Google sign-in do not independently settle the definition. Neither a policy checkbox nor Google's OAuth consent substitutes for ATT. No ATT prompt or `NSUserTrackingUsageDescription` is present in this snapshot. Therefore release requires either evidence that the chosen behavior does not track, or a compliant authorization/enforcement design that prevents tracking before permission and after denial/restriction. Adding a prompt without control of the embedded behavior would not close this gate. Do not suppress required YouTube advertising or silently change player behavior to manufacture a privacy answer.

The [privacy manifest](../../Sources/Muses/Resources/PrivacyInfo.xcprivacy) currently declares only UserDefaults required-reason access (`CA92.1`). It is not an App Privacy questionnaire or proof of no tracking. Validate the final archive's manifests and required-reason API usage after migration code merges; missing collection/tracking entries alone are not sufficient evidence to decide ASC answers.

## Immutable archives, provenance and per-item deletion

Additional source review requested by integration: `LegacyTrackArchive` in [LegacyArchive.swift](../../Packages/MusesPersistence/Sources/MusesPersistence/LegacyArchive.swift) retains original title/artist/album, duration, artwork URL and other scalars without field-level origin/fetch-time evidence. `LegacyQueueArchive` keeps raw JSON that can contain nested track snapshots. `LegacyModelArchive.fields` can include YouTube import titles, account channel IDs, playlist/item IDs, listening-event titles, inbox artwork, playlist revisions, remote shadows and sync-operation payloads. These are **possible API-derived or authorized data**, not proof that every old field came from Google: no actual private database was read. The absence of provenance prevents a claim that they are all original local user content.

`expireCatalogMetadata()` only iterates current `Track` projections. It does not inspect `.legacyTrack`, `.legacyQueue`, `.legacyModel`, nested JSON, the original SQLite store or physical recovery copies. Renaming those bytes “immutable,” “archive,” “migration,” or “rollback” does not establish a retention/revocation exception. The existing receipt in [LegacyUserTruth.swift](../../Packages/MusesPersistence/Sources/MusesPersistence/LegacyUserTruth.swift) hashes imported payloads and validates exact count/content on retry. Ad-hoc edits to archived payloads would break that contract; leaving them indefinitely also does not close the privacy gate. **Cross-migration retention design is required before release.**

Proposed classification/design for integration review (not implemented or approved by this document):

| Class | Evidence required | Intended retention/deletion handling |
| --- | --- | --- |
| Confirmed user-authored local content | Field-level provenance or a verified source contract: e.g. user-entered note text, explicit playlist name, favorite choice. A title-looking string or migration timestamp alone is insufficient. | Preserve in a durable user-truth projection during ordinary metadata expiry. Honor item removal and whole-app wipe, including specified recovery copies. Do not destroy a mixed record merely because some fields are API-derived. |
| Confirmed public API-derived fields | Provider/endpoint, original retrieval or last valid refresh time, purpose and copies containing the field. | Refresh/delete under applicable policy across live data and every app-controlled copy. Carry original age through migration; copying or importing must not reset the retention clock. |
| Confirmed authorized API data | Above plus account/authorization lineage: private playlist state, account IDs, remote revisions and embedded payloads. | Account-scoped invalidation/revocation and deletion must reach archives, shadows and copies as well as live pagers. Read-only permission is not indefinite retention permission. |
| Mixed or unknown provenance | Old title/artist/artwork, raw snapshot JSON, custom edits over remote values, missing timestamps or ownership lineage. | Mark unresolved; do not relabel everything `.user` or stamp a fresh fetch date. Design a lossless separation of provable user truth from remote/unknown material and fail closed for unverified API use. Isolating/encrypting bytes or withholding display does not itself satisfy deletion deadlines. If preservation and compliance cannot both be verified, block release and resolve the migration strategy. |

The migration design should explicitly version its recovery lifecycle: inventory source and every copy without modifying them; classify fields and nested payloads; extract and validate preserved user truth; produce a separately versioned sanitized successor; record transformation/deletion state durably; enforce expiry and user-deletion tombstones on every restore/import path. Design review must define when originals and temporary copies can be retired and what recovery remains possible after retirement. Migration verification and rollback must use the correct phase/receipt, with crash/retry tests. Do not rewrite the original digest to pretend sanitized data is the original import. A digest or tombstone prevents neither retention nor recoverability of bytes that still exist; they supplement actual disposal. This review does not authorize deleting sources, modifying receipts, or weakening rollback guarantees.

Per-item behavior also needs explicit product semantics. In [VideoNotebookRepository.swift](../../Packages/MusesPersistence/Sources/MusesPersistence/VideoNotebookRepository.swift), `deleteVideoNote`, `deleteVideoBookmark`, per-video clears and `stageVideoNotebookDeletion` remove mutable `.note`/`.bookmark` projections. They leave immutable archives/receipts unchanged. The current notebook alerts say a local note/bookmark is deleted and distinguish other entries, but do not explain that a migrated original could survive in a recovery copy. The bundled policy says local information remains until removed and later describes whole-app deletion of recovery data; it does not clearly distinguish item removal from recovery-copy erasure.

For the newly requested deletion of every Library item, review the **final integrated implementation**, not this snapshot, for an atomic deletion of active relationships and for resurrection through originals/archives. Current source includes the staging API but not proof that every new Library deletion path is wired. Required outcome: UI and policy specify the actual scope of item removal, any remaining recoverable copies and their bounded lifecycle; a working whole-app erasure route is available; required API-data deletion reaches retained copies regardless of labels. Disclosure alone cannot waive Google's deletion obligations. If the product intends permanent single-item erasure, a restore exclusion is insufficient while readable copies persist. Capture tests proving the selected semantics after migration, restart, retry and recovery. Until the retention/provenance strategy and these semantics are accepted, **P6-ARCHIVE remains an unresolved release gate**.
