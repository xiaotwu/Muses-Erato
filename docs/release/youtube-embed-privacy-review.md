# YouTube privacy-enhanced embed: evidence and release gates

Official-document review, 2026-09-27. Code baseline: `ebeedf4`. This work changes only static pages, documentation and the site builder; it does not change the app's player or determine a final App Privacy/ATT answer.

## Actual baseline versus an optional future mode

[YouTubeIFrameAdapter.swift](../../Sources/Muses/Platform/iOS/YouTubeIFrame/YouTubeIFrameAdapter.swift) loads `https://www.youtube.com/iframe_api` and constructs `YT.Player` without an explicit privacy-enhanced embed host. Its WebKit configuration uses the default persistent website store. Thus the current baseline must not be advertised as privacy-enhanced, cookie-free or tracking-free. The native ephemeral API transport is a separate data path. The generated website contains no player at all; the website's passive implementation does not alter the app's embedded-player behavior.

Google's [embedding help](https://support.google.com/youtube/answer/171780?hl=en) describes privacy-enhanced mode using `youtube-nocookie.com` for the **embed URL**. For applications, it directs use of the embedded website player inside a WebView. Its stated limits are specific: embedded views do not personalize the YouTube viewing experience; ads, if served, are non-personalized; those views do not personalize ads outside the site/app. Clicking out enters the destination's own policies. This is not a promise of no network requests, no identifiers/storage, no ads or no advertising measurement. The help also retains YouTube terms/policies and child-directed designation requirements. Do not infer that replacing only the IFrame API script's hostname enables this mode.

Any future implementation needs a separate player task: use a supported embed integration, verify the actual constructed iframe URL and behavior, and preserve API events, client identity/referrer, visible controls, ads, playback restrictions and user-intent behavior. The [IFrame API reference](https://developers.google.com/youtube/iframe_api_reference) describes controlling an existing iframe and the JavaScript API configuration. This documentation does not certify an untested host parameter or authorize player changes.

## Collection and ATT are distinct determinations

The binding [YouTube Developer Policies III.E.9](https://developers.google.com/youtube/terms/developer-policies) describe data transferred on player load for rendering, restrictions and abuse prevention, with additional processing on playback. Disabling autoplay limits pre-interaction sharing; it does not establish none. III.E.10 also requires handling Made For Kids status for embedded videos. A mode name does not override those obligations.

Apple's [ATT guidance](https://developer.apple.com/app-store/user-privacy-and-data-use/) considers linkage of app user/device data with other companies' data for targeted advertising **or advertising measurement**, and data-broker sharing. Functional web views are within scope; IDFA is not the only possible identifier. Therefore non-personalized ads are insufficient evidence by themselves to rule out tracking. Conversely, ads, cookies or an IP request do not independently prove the required cross-company linkage. A policy agreement or Google OAuth consent is not ATT permission.

Apple's [App Privacy guidance](https://developer.apple.com/app-store/app-privacy-details/) separately addresses retained off-device collection by integrated providers. Even when tracking is ruled out, applicable collected data, purposes and user linkage still need accurate disclosure. Review search history, video/product interactions, identifiers, advertising data and any diagnostic/location uses against actual evidence. The provider's broad privacy policy is context, not a Muses-specific field/purpose inventory. Do not copy Google app privacy labels into this app or mark “Data Not Collected” because Muses has no developer backend.

## Concrete evidence the owner/integration reviewer must obtain

| Gate | Evidence needed to close it | Limit of that evidence |
| --- | --- | --- |
| EMBED-MODE | If a mode change is proposed: tested build/commit, exact generated iframe host/path, approved integration reference, no fallback to standard embeds in error/queue/reload paths. If not changed, retain accurate standard-player disclosures. | A source string or homepage claim does not prove runtime mode; this review has no capture and changes no player. |
| PROVIDER-USES | Product-specific Google documentation or a recorded provider response explaining data classes, retention, identifiers, account linkage, ad measurement, cross-company joins and any broker sharing for the selected WebView mode. Record region/account/configuration scope. | Privacy-enhanced wording establishes limited personalization behavior; it does not answer every ATT question. If unresolved, privacy release sign-off remains blocked. |
| RUNTIME | Authorized device/build matrix: clean and returning WebKit stores; before app agreement; accepted/no play; cue/play/pause/seek; an ad when served; signed-out and signed-in Google browser states; sign-out; full deletion/restart; external YouTube navigation. Record endpoints and storage categories with synthetic data/redaction, including OS and region. | No ad appearing in a sample or no observed cookie is not proof of no processing/retention. Browser OAuth and app WebKit stores are separate. Do not save tokens or personal account traces. |
| ATT-DECISION | Written mapping of provider/runtime facts to Apple's tracking definition. If tracking occurs, verify permission precedes it and denial/restriction/revocation prevents it, including embeds. If claiming no tracking, record the evidence supporting that selected behavior and ongoing change monitoring responsibility. | Adding an ATT prompt without control over the provider's behavior does not solve enforcement. Do not remove mandatory YouTube ads or invent an unsupported opt-out parameter. |
| CONTENT-STATUS | Verify required Made For Kids handling and any applicable child-directed site/app designation against the final supported content and audience. Owner records the decision/evidence; no designation is changed here. | Privacy-enhanced mode alone is not a substitute for these requirements. |
| DECLARATIONS | Owner approves final App Privacy types/purposes/linkage/tracking answers and reconciles app policy, rendered privacy page, terms, consent UI and archived privacy manifest. Include evidence date and exact build. | Neither a successful static build nor OAuth brand approval approves these declarations. |

The baseline has no native ATT prompt observed. Do not conclude that one must be added solely from the presence of ads, or that it can be omitted solely from a potential privacy-enhanced mode. Resolve the evidence and effective controls first. Questions requiring platform/provider clarification belong in the owner's private review/verification channels; keep public Issues free of credentials and account traces.
